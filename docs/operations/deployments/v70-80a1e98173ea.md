## Camera takeover test

Snapshots came from Home Assistant's `camera.exterior_back_yard` `entity_picture`, read with the
existing read-only documentation token. `camera.fish` returned HTTP 500 from Home Assistant itself
(also when fetched from the build machine), and the frame correctly showed nothing for it.

| Test | Result |
|---|---|
| Single snapshot, 15 s, title | Pass: full screen with caption, slideshow back after 15 s |
| `refresh: 2`, 20 s | Pass: six fetches about 4 s apart (fetch time + refresh), then slideshow |
| Absolute URL on another host | Pass: ignored and logged |
| `dismiss` during a 120 s takeover | Pass: ended at once, slideshow back |
| `wake` while asleep on the schedule | Pass: screen awake with the snapshot, `displayActive` stayed false, dozing again after 15 s and still 35 s later, slideshow not started |

PSS stayed between 48 and 51 MB throughout. No fatal exception or ANR in the last 3,000 logcat
lines.

For the wake test the schedule was moved to end at 15:00, after a separate byte-for-byte backup,
and restored from it afterwards. A first wake attempt with the display turned off over RPC during
active hours turned the frame fully on: with Active Times enabled the 30-second schedule check (and
`onResume`) re-activate the frame during active hours, so an RPC or Home Assistant display-off only
lasts until the next check. That predates v70.

## Found, not fixed

- `/api/v1/info` returns `capabilities` as a string (`"[display, …]"`), not a JSON array: Android's
  `org.json` stringifies a Kotlin list, while the JVM `org.json` used by unit tests does not.
- `POST /api/v1/actions/camera` answers `ok` even when the URL is later rejected for its origin.
- During active hours the display switch does not stay off (above).
